# 性能测量

以下为 2026-10-29 本机 RTX 5080 / 120 Hz、默认约 224 px 角色的测量结果，描述应用进程 GPU 3D 引擎计数与 CPU/显存；不代表整卡功耗，也不能将整个 DWM 进程归给桌宠。

## 保留式 UI

三行工作会话、同材质对照：旧持续整窗重绘路径应用 3D 约 2.680%，最终 Windows Composition 路径两轮约 0.046% / 0.041%，面板基底从约 120 次/秒绘制降至约 1 次/秒（年龄更新）。此轮角色仍为旧帧动画，专用显存约 18.9 MiB；UI 的旋转与扫光没有取消或降刷新率。

系统合成器承担循环动画。DWM 在不同样本约 3.19%–4.39%，这是整个桌面的计数，不能据此推算桌宠的总 GPU 成本。切换 Mica 没有获得可归因的固定降幅，因此材质作为视觉选择保留。

## Spine 角色

采用默认小画布软件栅格路径后：仅角色时应用 3D 接近 0%，CPU 约 0.40%；含三行工作会话时，两轮应用 3D 约 0.082% / 0.067%，CPU 约 0.44% / 0.38%，专用显存约 18.92 MiB。可选原生 GPU 角色路径在该尺寸下约 0.9%–1.5%，故未作为默认。

这轮桌面流媒体采集已停止，DWM 计数没有可用于归因的数据，不能将零读数解释为全桌面 GPU 零成本。不同轮次的 GPU 时钟、桌面活动及采集状态会影响数据；这些数字不是通用保证。0.2.2 进行旧路径清理，没有重新声称获得额外 GPU 降幅。

角色普通 30 FPS，动作混合及短暂回弹期间 60 FPS；静态面板不因角色帧刷新。工作行共用两条合成器循环时钟，隐藏或移除后解绑，无工作行时停止。九个动作的 512 px 软件/硬件 PNG 参考对比，预乘通道平均差异低于 0.1/255，单像素通道差异均不超过 8/255。

## 复测

`scripts/profile-gpu.ps1` 使用本地固定场景，输出 `summary.json/csv` 和 `engine-samples.csv`，不写 ZCode、不记录会话内容、不保存诊断材质偏好，结束后恢复普通运行实例。采样时应记录显示器刷新率、GPU 时钟、流媒体采集和桌面活动。

可对照 `running` / `running-legacy`、`running-spine-gpu`、`running-no-shimmer`、`running-no-spinner`、`running-mica`、`running-solid`、`running-frozen`。`pet-frozen` 用于静态角色基线。应用计数与整卡/整个桌面的计数应分别解释。
## 0.2.5 CPU 观察侧优化

本机 16 逻辑处理器、默认 224 px 角色、真实数据约 461 条 message / 1720 条 part、当日日志约 1.2 MiB。独立连续观察微基准 24 次：单次墙钟耗时平均约 13.51 ms → 3.37 ms（约减少 75%）；进程检测约 6.18 ms → 0.49 ms，日志约 0.50 ms → 0.10 ms。该轮无等待查询的合格当前回合，旧全历史提问扫描约 3.91 ms，新路径跳过该查询。

三轮独立运行 24 次观察的整个进程 CPU 总耗时（包含诊断进程启动）为旧版 390.62 / 312.50 / 312.50 ms，新版 46.88 / 15.62 / 31.25 ms。这是观察诊断进程的对照，不能当成整个桌宠同幅降低。CPU 时间计数有约 15.6 ms 量化，单次 cpuUs 列不适合独立解释。

正常桌宠展开面板、每版 120 个约 100 ms 样本：平均 CPU 0.446% → 0.408%，最大短样本约 1.81% / 1.82%，P95 约 0.91% / 1.78%。短采样受计数量化、调度和角色动画节奏影响，不据此声称峰值下降；本机未复现用户报告的 5% 尖峰。角色软件栅格化仍有逐帧 CPU 成本，角色尺寸、机器和历史数据量都会影响结果。

实现：从经过可执行文件名校验的 ZCode 主窗口定位进程，无普通窗口时仍回退进程枚举；日志用文件身份、大小、修改时间和已读边界短签名识别追加/截断/替换，只解析新增完整行；当前回合的提问查询先限定 message_id，再使用现有 session/message 索引检索 part。无合格回合则不查询，不对用户库建索引、不改变两秒观察周期，不减少角色或 UI 动效帧率。

复测：`ZCodePet.exe --observer-benchmark` 在 EXE 旁写仅含阶段耗时与错误/在线标记的 observer-benchmark.csv；不含会话或日志内容。`scripts/profile-cpu.ps1 -BeforeExe <旧版EXE> -AfterExe <新版EXE> -OutputDirectory <输出目录>` 采集正常实例短间隔 CPU，最后默认恢复新版路径，可用 -RestoreExe 指定恢复实例。

## 3.0.0 内存与单文件

Windows 的 Working Set（常说的 RSS）是当前驻留物理内存的页面，会随页面回收、重新访问及运行库分配变化；它与私有提交量不是同一指标。单看 34–41 MB 来回变化，不能判定泄漏。本机未复现相同范围，因此没有把它归因于某一个查询或渲染动作，也没有使用强制裁剪工作集掩盖占用。参考 [Windows Working Set](https://learn.microsoft.com/windows/win32/memory/working-set)。

明确消除的重复分配：2048×790 RGBA 纹理原先先解码到约 6.17 MiB 临时数组，再复制到同样大小的常驻数组；现在 WIC 直接解码到最终数组。可选 GPU 后端完成不可变纹理上传后释放 CPU 纹理数组，软件后端保留必要采样数据。这减少加载峰值的重复缓冲，不代表常驻 RSS 必然下降 6.17 MiB。

正常实例展开面板、同一机器和设置、每版 150 个约 200 ms 样本（启动后等待 2.5 秒）：

| 指标 | 0.2.5 | 3.0.0 |
|---|---:|---:|
| 工作集范围 MiB | 69.88–72.88 | 71.40–73.62 |
| 平均工作集 MiB | 71.24 | 72.76 |
| 私有提交量范围 MiB | 72.41–74.44 | 72.06–74.09 |
| 平均 CPU | 0.403% | 0.433% |
| 最大短样本 CPU | 1.33% | 1.37% |

本轮没有证据证明常驻工作集下降，也没有观察到明显的 CPU 回退；采样时序和合成器活动会影响结果。各约 30 秒的采样不足以证明长期无泄漏，用户设备的波动仍需同看私有提交量趋势。`profile-cpu.ps1` 的 `cpu-samples.csv` 增加 WorkingMiB、PrivateMiB、PeakWorkingMiB，方便复测。

资源改成 PE 内嵌、直接从内存读取，不在启动时解压临时文件；CRT 静态链接，发行只需要一个约 2.4 MiB 的 EXE。用户偏好仍位于 LocalAppData，不随运行目录迁移。完整许可与署名也内嵌，可通过工具栏或 `--licenses` 查看。18 项测试包含无伴随文件的独立目录测试。
